# Requirement—Architecture—记忆与可追溯性演化参考

> 文档定位：记录 ProjectOS 后续设计的判断、边界与待验证方向。它不是当前运行协议，也不代表其中的未来方案已经实现。
>
> 记录日期：2026-09-17

## 1. 当前已验证的范围

ProjectOS 已验证一个真实的 Architecture 最小顺向闭环：

```text
Requirement
→ Architecture Blueprint
→ 动态 Module Design
→ 动态 Implementation Design
→ Integration
→ Quality Gate
→ 正式架构发布
```

当前实现的 Architecture 采用“固定三类设计深度、动态模块展开”：

- Blueprint 是 `depth=0`；
- Module Design 是 `depth=1`；
- Implementation Design 是 `depth=2`；
- Blueprint 决定模块的数量、职责与依赖；
- 控制面按真实模块清单动态生成 Module 和 Implementation 工作项；
- 最终由 Integration 汇总并由 Quality Gate 发布。

这证明了产物协议、依赖屏障、正式发布证据和部分恢复校验可以支持一次真实运行。它不证明用户意图确认、跨层自动纠偏、Code/Runtime 全链路或长期成功率已经解决。

## 2. 核心系统风险：顺向继承不等于持续正确

当前系统主要验证“下游产物是否符合上游产物和自身合同”，但尚未完整验证“上游产物是否忠实表达用户真实意图”。因此链路存在以下风险：

```text
用户原始意图
→ Requirement 解释候选
→ Architecture 继承 Requirement
→ Code 继承 Architecture
→ Runtime 只验证已被明确表达的目标
```

如果 Requirement 漏掉了身份、权限、持久化、错误行为等隐含条件，后续节点可能都能相对一致地实现错误方向。后续产物越多，修正成本越高。

特别要区分：

- Requirement Agent 生成的内容，在没有用户确认前只能视为需求解释候选；
- `requirement.md` 的结构合法，不代表需求完整或符合用户真实意图；
- Architecture 覆盖 Requirement，不代表 Architecture 覆盖了未被 Requirement 表达的目标；
- 一次 Architecture 发布成功，不代表整个系统语义正确。

## 3. 过程产物、状态、记忆和校验的职责

| 机制 | 应承担的职责 | 不应替代的能力 |
|---|---|---|
| 过程产物 | 保存可引用、可验证、可版本化的设计结果 | 不替代用户确认和业务判断 |
| 运行状态 | 记录当前阶段、依赖是否完成、是否允许推进 | 不证明产物内容正确 |
| 决策记忆 | 保存已确认决策、约束、假设、未解决问题及理由摘要 | 不替代正式产物、权限和版本关系 |
| 确定性校验 | 检查结构、引用、版本、接口覆盖和约束 | 不保证模型业务判断正确 |
| 恢复机制 | 在输入、产物和副作用仍有效时复用或重做 | 不应盲目恢复到已经失效的方向 |
| 用户确认 | 冻结用户认可的需求版本和重要取舍 | 不能由模型或日志隐式代替 |

未来的“过程产物 + 记忆”混合模型，不应是把聊天记录全部塞进上下文，而应是：产物保存结果，决策记录保存理由与未决事项，控制面按当前任务选择性组装上下文。

## 4. 未来应形成的需求追溯关系

在完整系统中，后续节点不应只依赖上一层产物，还应能追溯到已确认需求：

```text
Confirmed Requirement R1: 用户可以创建任务
├── Architecture A1: 创建任务模块与接口
├── Code C1: 创建任务实现
└── Runtime V1: 创建任务验收
```

每个需求条目最终应能够回答：

1. 是否已被确认；
2. 哪个架构责任覆盖它；
3. 哪个实现单元兑现它；
4. 哪个运行时检查验证它；
5. 是否存在未解决假设或冲突。

这不是要求每个 Agent 读取完整聊天历史，而是建立版本化的需求条目、覆盖关系和验证证据。

## 5. 设计纠偏方向

当前最重要的缺口不是单纯增加更多记忆，而是缺少受控的反馈修订通道：

```text
子节点发现当前约束无法满足
→ 记录问题证据与修订请求
→ 父层决定修订、澄清或拒绝
→ 生成新的父层版本
→ 计算受影响的下游产物
→ 仅使受影响部分失效并重新执行
```

子节点不得越权直接修改父层；父层修订也不能让旧的下游结果继续被默认为有效。未来需要明确：

- 什么情况必须上报，而不是局部猜测；
- 谁拥有边界、接口和全局约束的修改权；
- 如何表示 unresolved issue、assumption 和 decision；
- 哪些下游结果因父层版本变化而失效；
- 哪些结果可以在新版本下重新验证后复用。

## 6. 当前阶段的明确取舍

当前优先级是先完成：

```text
Architecture 产物
→ Code 真实实现
→ 集成与启动
→ Runtime API/UI/持久化验收
→ completed
```

暂不因为上述长期问题而立即引入：

- 完整多轮聊天入口；
- 大型长期记忆库或向量记忆系统；
- 任意深度递归 Architecture；
- 自动父层修复和全局智能回溯；
- 未经实验验证的多套并行 Agent 角色。

原因是这些设计应由真实 Code/Runtime 失败、需求返工和上下文丢失数据驱动。当前应保留可扩展的需求引用、假设和验证关系，但不提前建设完整最终形态。

## 7. 后续验证问题

完成最小实现闭环后，用真实实例回答：

1. Architecture 产物是否足以驱动 Code，而不是只适合发布设计文档；
2. 哪类偏差最早暴露，发生在需求、架构、实现还是运行时；
3. 失败重试时，重新读取正式产物是否已经足够；
4. 哪些决策理由和未解决问题若不保存，会导致重复错误；
5. 需求追溯是否比增加上下文长度更能降低返工；
6. 哪些内部步骤值得成为独立恢复边界。

只有在这些问题产生真实数据后，才决定混合记忆和自动纠偏的实施粒度。

## 8. 当前结论

ProjectOS 当前拥有的是一个**可运行的顺向 Architecture 产物链路**，不是一个已经完成用户确认、跨层追溯和持续纠偏的智能项目系统。

后续演化原则：

> 先让产物驱动真实实现和 Runtime 验收，再用真实偏差决定记忆、确认、追溯和反馈机制；不要用记忆层掩盖错误的设计边界，也不要把一次成功运行误认为系统性正确。
